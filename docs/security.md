# Security and operational boundary

Default: local Demo/Research. On2026-11-25 the user first authorized existing Alpaca settings for market-data GET requests, then explicitly requested actual paper trading. The historical adapter still permits only two GET paths on data.alpaca.markets. The separate opt-in paper CLI fixes the trading host to https://paper-api.alpaca.markets, rejects live-host configuration and redirects, and permits only account/clock/position/order/asset reads, simulated equity limit-order submission and individual cancellation. No live-money route, account-wide cancellation, account configuration or liquidation endpoint is allowed. Credentials remain in memory; no prior dataset is reused. `.env`, raw snapshots and all paper account/order/journal records are ignored.

Paper scope: initially a $5,000 strategy budget/$1,000 slot, subsequently increased by the user to a $100,000 ceiling/$20,000 slot. Whole long-only shares, USD cash rather than margin buying power, regular-session DAY limit orders, validated fresh historical inputs and next-open execution window. Existing positions must reconcile to the strategy's actual filled quantities; unknown positions/orders stop execution. Durable SQLite intent precedes POST; a deterministic account/strategy/session/symbol/revision ID, local process lock and broker lookup prevent duplicate submissions. Budget changes require a paused scheduler, own pending cancellation confirmation, a position recheck, journal backup and a durable revision/audit entry; they never erase fill history. Ambiguous POST outcomes stop without blind retry. STOP blocks new submissions; cancellation affects only journal-owned pending orders. A stop file does not itself cancel an order already accepted by the broker. Paper operations are CLI-only and not exposed through the web API. See PAPER_TRADING.md for status and recovery limitations.

The subsequent automatic-trading request authorizes a local5-minute LaunchAgent using the same budget/account/journal. It collects missing completed sessions into a separate private rolling cache and evaluates next-session targets after close+10minutes. Scheduler state/locks and bounded read/data retries prevent repeated work; ambiguous orders or permanent data/account faults latch blocked until explicit resume. Unfunded entries are deferred without preventing owned-share exits. macOS folder access must be granted through the OS; no privacy settings or credential values are changed by the installer. See PAPER_AUTOMATION.md for pause/uninstall and awake/login requirements.

`QUANTCORE_API_TOKEN` optionally protects `/api/*` with constant-time bearer comparison. Capability is a single researcher role: read data and request calculations; no administration or order submission API exists. This is not multi-user RBAC. `/health` is anonymous. Rate limit: 180 API requests per client/IP per minute, in-process memory. CORS restricts configured local dashboard origins.

Browser WebSocket obtains a 30-second, single-use random ticket via authenticated API; raw API secret is not embedded into browser code. Origin must be allowed, ticket is consumed, reused tickets fail. HTTP BFF stores API token server-side. The BFF is intended for a loopback single-user dashboard; it is **not** a substitute for browser user authentication. Before remote exposure, add user authentication/authorization, TLS/reverse proxy, persistent/distributed rate controls and secure audit retention.

Pydantic validates finite values and ranges; SQLAlchemy/DuckDB bind parameters. No user-provided URL fetch or arbitrary code execution. API computation inputs are bounded; long-running research requests should be queued before multi-user deployment.

Audit records ingestion insert counts and failures. SQLite online backup uses a new destination, integrity_check and digest; recovery should be rehearsed before production. Secrets must not be written to audit logs. Filesystem backup destination and environment config are operator privileges, not exposed through HTTP.

Actual analysis API deployment: no Alpaca/APCA secret is passed to API/web containers. The authorized host collector owns authenticated market-data access; API reads its snapshots via a read-only bind mount. It runs as an unprivileged host-matching UID so future umask077 snapshot files remain readable. A controlled permission probe confirmed read access and EROFS on write. Snapshot paths resolve within configured provider directories, hashes/timestamps/OHLC/universe and overlap consistency are validated, and invalid sources return503 without synthetic substitution. The web proxy keeps optional API authentication server-side; the existing paper client and order journal are not mounted into this API.
